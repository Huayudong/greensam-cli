# 启动脚本 greensam-cli.cmd 编码与透明加密修复

- **日期**：2026-08-31
- **背景**：用户在默认中文控制台（GBK 代码页）执行 `bin\greensam-cli.cmd` 报
  `'o擢Ⅰ?' 不是内部或外部命令`，脚本无法启动。排查发现是**两个独立问题叠加**。

## 一、问题定位

### 1.1 仓库里的脚本是密文（企业透明加密 / DLP）

本机装有按进程白名单做透明加密的 DLP（文件头 `%TSD-Header-###%`）：

- 授权进程（IDEA 等）写文件 → 落盘即加密；授权进程读时透明解密，无感知；
- 未授权进程（python、cat、git、ZCode 的读写工具）看到的是原始密文。

原 `greensam-cli.cmd` 由授权编辑器创建（2026-08-28），落盘即密文，**git 把密文原样
提交进了仓库**（`git show HEAD:bin/greensam-cli.cmd` 即密文，8192 字节）。
也就是说：GitHub / 新人 clone 到的启动脚本对 DLP 环境之外完全不可用。
仓库其余文件均为明文（由未授权进程写入，DLP 不加密未授权进程的写入）。

**辨别方法**：`od`/`file`/`iconv` 属授权侧（看到明文），`cat`/`python`/git 属未授权侧
（看到密文）——同一文件两个视图，排查时极易被误导。

**修复原则**：用未授权进程写入的文件保持明文落盘（本仓库所有经 ZCode 写入的
源码即是明文的实证）。本次用 ZCode 写工具重写脚本后，python 复核无 TSD 头、
git diff 恢复为正常文本差异。

### 1.2 cmd 批处理 + UTF-8 中文 = 解析撕裂（与 DLP 无关的第二个 bug）

用户本机 cmd.exe 是授权进程，能透明解密看到明文，但仍然崩：脚本原版把
`chcp 65001` 放在中文注释**之后**，GBK 代码页先撕碎了前面的中文行。

修复过程发现更深一层：**即使把 `chcp 65001` 提到第一行，中文行依然被撕**——
错误显示正确解码的 UTF-8 文本（如 `用法:`）被当作命令执行，即 `rem` 前缀丢失。
这是 cmd 对批处理文件的**字节偏移回卷缺陷**：65001 代码页下存在多字节行时，
解析位置漂移到行中间，把行尾当命令（Win11 26200 实测复现，chcp 前置无效）。

**结论：Windows 批处理文件只要涉及代码页切换，唯一可靠做法是全 ASCII。**
中文注释由 `.sh` 与文档承载，控制台中文由 JVM 侧 UTF-8 参数渲染（与脚本无关）。

## 二、变更点

- `bin/greensam-cli.cmd` 重写：**全 ASCII**（含错误提示），CRLF 行尾，
  `chcp 65001 >nul` 保留（供控制台与 JVM 输出配套），java 启动参数不变。
- 明文落盘（1219 → 1251 字节），git 可正常提交；远端仓库的密文历史 blob
  不做改写（无危害），本次提交后新内容即正确。

## 三、验证结果

- python 复核：无 TSD 头、CRLF 33 处、非 ASCII 字节 0 个；
- 功能验证（Git Bash 内 `cmd /c` 执行，管道输入 `/exit`）：**零错误行**，
  banner 中文正常渲染，退出码 0；
- GBK 控制台场景：脚本全 ASCII，与代码页完全解耦，任何控制台均按同一字节解析。

## 四、遗留风险与建议

- 本机 DLP 会持续对授权进程写入的文件做落盘加密——**IDEA 等编辑器新建/保存的
  仓库文件都有被加密提交的风险**。建议在 DLP 管理端将仓库目录加入明文白名单，
  或提交前用 `git diff` / python 抽查文件头是否为 `%TSD-Header-###%`。
- `.env`（含 API Key）本身是明文且被 `.gitignore` 排除，不受影响。
