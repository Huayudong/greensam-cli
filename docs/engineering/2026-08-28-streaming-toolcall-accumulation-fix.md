# 流式工具调用累积修复：空值覆盖导致「未知工具: 」与 SSE 前缀容错

- **日期**：2026-08-28
- **作者**：Macro Ray
- **状态**：已完成，106 个测试全部通过

## 任务范围

修复流式模式下的高频工具执行失败：LLM 请求调用工具时，终端渲染为
`🛠️ 调用 ({...})`（工具名缺失），`ToolRegistry` 抛出 `未知工具: `（空名字），
Agent 循环反复重试直至放弃。规律：**参数短的调用（一个分片装得下）成功，
参数长的调用（arguments 跨多个分片）必失败**。

## 根因

OpenAI 兼容协议的流式增量中，`id` / `type` / `function.name` 只在**首个分片**
出现，后续分片只有 `arguments` 片段。部分兼容端点在后续分片里会**重复下发
`id:""` / `name:""`（空串而非字段缺省）**。

原累积逻辑用 `tcDelta.has("name")` + `!isNull()` 判断是否写入——空串字段
照样命中，于是每个后续分片都把首个分片累积到的真实 id / name **覆盖为空串**：

- `name` 被清空 → `ToolRegistry.executeTool("")` → `未知工具: `（本缺陷）；
- `id` 被清空 → 工具结果回传的 `tool_call_id` 失配（潜伏问题，本次一并修复）。

用 curl 向实际端点抓取原始 SSE 分片确认了上述行为（复现证据，仅作验证记录，
修复本身不依赖任何具体端点）。

## 设计口径（重要）

**修复是协议级的统一归一化规则，不是针对任何厂商的特判**：

> 增量累积时，`id` / `type` / `function.name` 只接受**非空值**写入；
> 字段缺省、null、空串一律忽略。`arguments` 是唯一允许跨分片追加的字段。

该规则对「只在首片出现」「每片重复全量」「后续片发空串」等所有符合
OpenAI 兼容协议的分片行为一律成立，换模型、换网关、换本地部署都无需再改。
若将来接入非 OpenAI 协议（Anthropic / Gemini 原生等），正确做法是新增
实现 `StreamingChatClient` 接口的适配器，而不是在现有解析里加分支。

## 变更点

| 文件 | 变更 |
|------|------|
| `client/OpenAiStreamingChatClient.java` | ① 工具调用增量累积改为「非空才写入」：`id` / `type` / `name` 经 `path(...).asText("")` 归一后仅非空写入，`arguments` 保持追加；② SSE 行解析兼容 `data:` 带与不带空格两种前缀（SSE 规范均允许，部分网关发紧凑形式） |
| `test/client/OpenAiStreamingChatClientTest.java` | 新增 2 测试：后续分片空串 id/name 不得覆盖真实值（含 arguments 分片拼接断言）；紧凑 `data:` 前缀可正常解析 |

## 验证

- `mvn test`：106 个测试全部通过（流式客户端 2 → 4 个）。
- 新增回归测试锁死协议契约：空串覆盖场景若回归，测试立即失败。

## 遗留风险

- 部分端点将 `function.name` 跨分片拆开传（未见主流实现）不在规则覆盖内，
  若真遇到应在该端点的适配层处理，不改统一累积规则。
- 事发现场对话历史里 `tool_call_id` 为空串的旧会话无法追溯修复；
  新会话不受影响。
